# Compliance and control matrix

Version 0.5.42 · reviewed 2026-10-15 · **Reference** · audience: auditors, compliance owners, security engineering

> Describes the v0.5.42 source. Automated evidence is listed in [staging validation evidence](assurance-plan.md#staging-validation-evidence-2026-10-15); it does not establish release publication, production operation, or SOC 2 effectiveness.

Framework requirements mapped to implementation and test evidence in this
repository, with honest status. The defensive design is in
[security.md](security.md); threats are in [threat-model.md](threat-model.md).
For the SOC 2 and ISO/IEC 27001 mapping, see
[soc2-control-mapping.md](soc2-control-mapping.md). For the plan that will test
these controls, see [assurance-plan.md](assurance-plan.md).

> **This is a traceability baseline, not a certification, attestation, or audit
> opinion.** It does not claim that any inherited control operates effectively.
> Evidence cells name only repository artifacts or commands observed on the
> stated date. Empty operational evidence means no verified operating record was
> supplied.

> `CM-###` identifiers are **stable**. Entries are retired in place, never
> renumbered or reused.

## Status vocabulary

| Status | Meaning |
| ------------- | ----------------------------------------------------------------------------------- |
| **Evidenced** | An observed command or a named test proves the requirement in this repository. |
| **Partial** | Some evidence exists; a specific named piece is missing. |
| **Planned** | Requirement and owner are defined; implementation or test evidence is insufficient. |
| **Gap** | Observed repository state conflicts with the requirement. Release-blocking. |
| **Inherited** | The control belongs to another service or team. See the rules below. |

## Rules for inherited controls

An inherited control satisfies nothing here until it (a) names the service and
responsible owner, (b) defines the desktop-side integration obligation, and
(c) links current, independently verified operational evidence. Contracts,
documentation, and assumed cloud behaviour are **not** operating evidence.

Product Engineering remains responsible for safe integration and fail-closed
behaviour even where a control is inherited. Unknown retention, backup, erasure,
tenant-isolation, key-management, signing, or audit values remain recorded as
risks and are never filled in with estimates.
