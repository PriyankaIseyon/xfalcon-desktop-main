## Invariants

1. **122 commands, 122 `allow-*` permissions, 4 plugin permissions.** Exactly 1:1
   between commands and `allow-*` entries. The two macOS-only window permissions are outside this count. The tests
   `command_surface_is_the_exact_explicit_allowlist`,
   `every_registered_command_has_a_generated_permission`, and
   `every_registered_command_is_admitted_by_the_window_capability`
   (`src-tauri/src/security/tests.rs`) assert it against `APP_COMMANDS`.
2. **The renderer never names a filesystem path for project or skill actions.**
   The Rust side opens the folder and file dialogs. It returns an
   opaque grant id, 32 hex characters, that expires after 15 minutes. `project_create`,
   `project_find_by_folder` and `skill_import` take that grant id. The renderer
   can send a grant id for another kind, or one that has expired. The backend
   refuses it. Every other path argument is project-relative, inside an
   already-trusted root. Grants are described in
   [Path grants](#path-grants).
3. **No command returns a secret.** Provider keys, tokens, grants, and envelope
   ciphertext never appear in a projection. `McpServerView` carries the OAuth
   client id (not confidential) and a flag, `oauth_client_confidential`, but never
   the client secret.
4. **The renderer may listen but not emit.** `core:event:allow-listen` and
   `allow-unlisten` are granted; emit is not. The renderer cannot forge a
   backend event to itself or another window. The renderer has no dialog
   permission (`dialog:allow-open` was removed).
5. **Forbidden forever.** `run_shell`, `write_file`, `write_text_file`,
   `read_file`, `read_text_file`, `fetch_url`, `get_credential`, and
   `upload_file_chunk` are pinned in `FORBIDDEN_COMMANDS` whose cardinality is
   asserted, so it cannot grow or shrink silently.

## Adding a command

Six production places, in this order. The security test will name whichever you forget.

1. `crates/contracts/` — the argument and return types.
2. The module's `commands.rs` — a thin `#[tauri::command]` over a service method.
3. `src-tauri/src/security/capabilities.rs` — add the name to `APP_COMMANDS`.
   That is the allowlist. Tests do not have a second copy.
4. `src-tauri/src/lib.rs` — `use` it and add it to `generate_handler!`.
5. `src-tauri/build.rs` — add it to `AppManifest::commands` so the permission
   file is minted.
6. `src-tauri/capabilities/default.json` — add `allow-<command-name>`.

Then regenerate the permission file and the TypeScript contracts, and add the
`native.ts` wrapper. See [contributing.md](contributing.md) for the exact
commands, including the stale-`.toml` gotcha.

## Commands

Argument names are camelCase on the wire (Tauri's convention); Rust parameters
are snake_case. `→` gives the return type from `crates/contracts`. Payload fields
inside contract types are snake_case. [Errors](#errors) lists what each group
rejects with.

### Application lifecycle — 4

| Command            | Arguments | Returns                                                                                                                                                                                                      |
| ------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `app_bootstrap`    | —         | `AppBootstrap` — `application_version`, `platform`, initial `session`                                                                                                                                        |
| `app_health`       | —         | `AppHealth` — `status` is `ready` or `degraded`                                                                                                                                                              |
| `app_reset` | —         | `void` on success. A string error when the reset helper could not start, or a reset is already under way. |

`app_reset` is the full local reset, and the only in-app erase command. Its side effects, in order: it starts the reset helper, which is a detached copy of the app that purges after the app exits (retries, relaunch when installed); it records `data.erase` with resource id `device` and outcome `allowed`, or `failure` with detail `not_started` when the helper did not start; it runs the account clear (`clear_account_state`, the first step of Reset), bounded at 10 seconds, and ignores its result; and after 400 ms it calls `exit(0)`, even when the clear timed out. A second call while the helper is running returns "A reset is already under way. xFalcon will close and reopen on its own." and writes no audit event. Capability: `allow-app-reset`. Settings > Data & reset hosts that one entry point, Reset xFalcon. See [data-lifecycle.md](data-lifecycle.md) § Erase method 1.

`chat_mcp_selection_get(conversationId)` returns `ChatMcpSelectionView`
(`version: 1`, `server_id: McpServerId | null`). The ID is `null` for All servers.
It rejects malformed stored bindings. Every submission and upload reservation
validates the requested selection against the conversation binding. A specific
selection includes a native-resolved endpoint in conversation metadata; removed,
unavailable or repointed servers fail without falling back to All. Changing the
composer selection starts a fresh chat and preserves the previous chat.

`chat_message_send` never rejects. It returns a `ChatSubmitResult` with
`status: "failed"` and a message for each of these cases, each with a distinct
message: an empty prompt with no attachments, a prompt over 524,288 bytes (512 KiB,
`MAX_MESSAGE_TEXT_BYTES` in `src-tauri/src/chat/domain.rs`, measured after
trimming), more than 64 attachment ids, an attachment id that is not a UUID, an
unauthenticated caller, a send already in flight, a 9th concurrent run
(`MAX_IN_FLIGHT_RUNS` is 8), and an update install in progress (`update_restart`). Ready chat
attachments are bound by DA resource id; on `submitted` the backend drops the
matching queue rows so chips do not linger. `chat_message_edit`,
`chat_message_regenerate`, and `chat_run_retry` return a `ChatSubmitResult` or
reject with a `ChatOperationError`.

`chat_tool_approval_resolve` mints a token scoped to that exact invocation and
tool inside that run's own `ToolLoop`. It grants nothing else. Note that the
product default auto-approves tool calls, so this command is normally only
reached when `XFALCON_REQUIRE_TOOL_APPROVALS=1` is set
([decisions.md](decisions.md) ADR-008).

### Uploads — 5

| Command         | Arguments                                                      | Returns                                                                           |
| --------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `upload_choose` | `conversationId \| null`, `mcpServerId \| null` | `UploadQueueV1` — opens the native attachment picker in Rust                      |
| `upload_paste`  | `conversationId \| null`, `name \| null`, `dataBase64 \| null`, `mcpServerId \| null` | `UploadQueueV1` — clipboard bytes, or the OS file references when both are `null` |
| `upload_cancel` | `uploadId`                                                     | `UploadQueueV1`                                                                   |
| `upload_retry`  | `uploadId`                                                     | `UploadQueueV1`                                                                   |
| `upload_queue`  | —                                                              | `UploadQueueV1`                                                                   |

The webview never receives a filesystem path or presigned URL. Chat attachments
are capped at 10 MiB (`MAX_CHAT_ATTACHMENT_BYTES`) and transfer immediately after
the picker confirms. `UploadProjectionV1` carries `id`, `purpose`, `state`,
`bytes_sent`, `size`, `display_name`, `safe_error`, and optionally the DA
`resource_id` and the `conversation_id`. `upload_paste` needs the main window to be
focused. It refuses `name` without `dataBase64`, and the reverse.

With `conversationId: null` -- a new chat with nothing sent -- the picker opens
(or the clipboard is read) first, and only a file actually chosen reserves an
unopened conversation, which the queued upload names. A cancelled picker creates
nothing, and a file refused after reservation deletes the reserved conversation
again. The renderer sends the first message into the reserved conversation and
opens it then, and deletes it if the person leaves the new-chat screen instead.

Before a run, the backend lists the conversation's ready attachments and puts
each back on the user turn it was sent with: images as image parts, text, CSV,
TSV and workbooks as delimited text bounded by the run's result budget, and any
file it cannot read as a note naming it, and a file the allowance cannot hold is
named without being downloaded (`src-tauri/src/chat/attachments.rs`). An
unreadable attachment list fails a run that answers a message sent with files; any
other run goes ahead without earlier files. `chat_message_send` fails when DA links
fewer attachments than were sent. The reserved conversation is kept out of the
sidebar until its first message.

`project_create` and `project_find_by_folder` accept only a grant id from
`project_pick_folder`. A grant is kind-checked, lasts 15 minutes, and is not used up
by a call, so the folder flow can resolve it twice. An unknown, expired, or
wrong-kind grant is refused with the text `That choice expired. Choose it again.`
The file view reads with
`project_file_stat` first, then
`project_file_read_bytes` in ranges of at most 8 MiB: a file up to 64 MiB is
assembled whole, a larger one (up to 10 GiB) is paged a window at a time. Every
call re-checks sensitivity and containment, and reads size and modified time
from the handle it reads. The only state kept between calls is
`project_table_rows`' row index, keyed by project, path, the file's size and
modified time, and delimiter, so a changed file is indexed afresh. The cache holds
8 indexes (`src-tauri/src/projects/table.rs`). A cell is cut at 16 KiB and a
table at 1,024 columns for display, and the window is then marked `truncated`.

Office project text uses `project_document_read` after the same fresh
sensitivity and trusted-root checks. The parser reads only the opened file,
does not run Office or fetch external resources, and returns text only. It does
not OCR images or preserve visual layout, fonts, or styling. The command rejects
encrypted, malformed, unsupported, or over-limit files and rechecks the opened
handle's size and modified time after reading bytes and before extraction. The
frontend stats the file again after the command to detect changes during the
read. `project_file_read_bytes` still returns the original Office bytes;
extracted text is not editable or saved back to the source. A valid blank or
image-only file can return empty text; the viewer explains that no text was
extracted and that images are not OCR-scanned.

`project_office_preview` reads through the same trusted-root boundary and makes a
PDF from a temporary copy by asking a program that is already installed (nothing
is bundled or installed) to export it, hidden, with macros off and the file opened
read-only. Microsoft Office (Word, PowerPoint or Excel) is used when present;
only when it is not installed is LibreOffice tried, and on Windows then WPS Office
(`.docx`, `.pptx` and `.xlsx` only). An installed program that fails gives the
answer; the next one is never used to get around it. Windows drives Microsoft
Office and WPS Office through COM from a fixed PowerShell script; macOS drives
Microsoft Office through a fixed AppleScript per program (not yet run on a Mac);
LibreOffice runs headless on both. None of the fallbacks has been run on a machine
that has it. Paths reach the script as arguments,
never as script text. One conversion runs at a time. Starting another cancels
the old job and waits for it to stop. Navigation, project revocation and account
changes cancel pending work, and a cancelled or timed-out job stops the Office
process it started. The command checks the original's hash, size and modified
time again before returning PDF bytes. Input is limited to 32 MiB, output to
64 MiB and execution to 120 seconds. When the program is missing, the file is
protected or blocked by Office security settings, or the platform is unsupported,
the command fails with a readable message and the extracted Text still loads.
The viewer opens on the preview, so selecting a file starts the conversion; switching between its Preview and Text views does not. A finished PDF is also kept in memory, keyed by account, project, path and a SHA-256 of the source bytes (8 PDFs or 128 MiB, least recently used first, never written to disk), so reopening an unchanged file returns it without starting Office and any change to the file makes a new one. The source is read through the trust gates before the cache is consulted.

The finished PDF is kept for 15 minutes under the preview's id so
`project_office_save_pdf` can write it without the renderer sending bytes back.
Both save commands open the native dialog on the Rust side: the destination comes
from the operating system, never from the caller. Excel files take the same
preview and save path but have no text extraction.

`ProjectFileStat` is one of `text`, `not_text` (with a `reason`: `binary`,
`non_utf8_text`, or `oversized`), `too_large`, or `sensitive_withheld`.
`ProjectFileRevisionDiff` is one of `changes`, `unchanged`, `not_text`,
`too_large` (with a `limit`: `file_size` or `change_size`), or `sensitive_withheld`.

`project_file_revision_diff` looks both revisions up in that file's own history,
so an id from another file is not found. It applies the file view's sensitivity
gate before either side is read, checks the stored size before it decrypts the
revision, and runs off the main thread.

`project_save_file`, `project_file_revisions`, `project_file_revision_diff`, and
`project_file_restore` reject with `NoActiveAccount` text when no account is signed
in. `project_save_file` has no review step: these are local files the operator
chose to trust and a person saving their own edit has already reviewed it. The
backend still plans, journals, audits, and re-validates containment before
writing.

### Provider credentials — 4

| Command              | Arguments                                  | Returns                                                         |
| -------------------- | ------------------------------------------ | --------------------------------------------------------------- |
| `credential_list`    | —                                          | `ProviderCredentialView[]` — redacted projections               |
| `credential_create`  | `provider`, `label`, `secret`, `isDefault` | `ProviderCredentialView`                                        |
| `credential_replace` | `id`, `secret`                             | `ProviderCredentialView`                                        |
| `credential_delete`  | `id`                                       | `void` — deletes the row through DA, for every signed-in client |

`provider` is `openai`, `anthropic`, `google`, `openrouter`, or `custom_openai`.
`status` is `ready`, `disabled`, `needs_reentry`, or `verification_failed`. Create
and replace verify the secret with the provider before they write.

`credential_replace` re-seals an existing key to this device, keeping its row,
label, and default flag. That is what a `needs_reentry` status asks for: re-adding
under the same label collides with the workspace uniqueness rule, and under a new
label the unusable row would survive holding the default flag. An id that names no
row is refused as `invalid_request`.

`credential_delete` re-reads the list under the credential mutation lock. It
sends to DA only an id that list contains. An id that is already gone succeeds and
deletes nothing, so a stale settings screen cannot delete a different row. A DA
answer that names another row, or no answer, reports `reconciliation_required`
(`src-tauri/src/clients/da/provider_keys.rs`), and the renderer reloads the list.

## Path grants

A grant is an opaque id that stands for a folder or a
set of skill source files that the person picked in a native dialog. The backend
keeps the real paths. The renderer receives only the id and display text.

| Rule            | Value                                                                                                          |
| --------------- | -------------------------------------------------------------------------------------------------------------- |
| Id              | 32 hex characters, random (128 bits)                                                                           |
| Kinds           | `folder` (project commands) and `skill_sources` (skill commands). A grant of one kind is refused by the other. |
| Lifetime        | 15 minutes                                                                                                     |
| Live grants     | At most 16. The oldest is evicted first.                                                                       |
| Paths per grant | At most 4,096. A larger selection is refused with a warning. It is never cut short.                            |
| Reuse           | Not used up by a call.                                                                                         |
| Cleared         | At sign-out and in the account clear (the first step of Reset xFalcon).                                                                           |

Commands that issue a grant: `project_pick_folder` and `skill_pick`. Commands
that take one: `project_create`, `project_find_by_folder` and `skill_import`. A
skill drop on the window emits `xfalcon://skill-sources-dropped` with a grant
view. The native dialogs and the real OS drag events are UNVERIFIED end to end.
No window was run. The grant logic and the event mapping have unit tests.

`src-tauri/src/app/events.rs`), is defined with an `emit_runtime_event` helper
that carries a `RuntimeEvent`. No production code calls the helper and the
renderer does not listen to it.

### Chat and upload channels

Constants in `src/features/chat/chatChannels.ts`. Rust has the same names in
`src-tauri/src/app/events.rs`, except `xfalcon://upload-queue`, which
`src-tauri/src/lib.rs` and `src/lib/native.ts` spell out. `chatStore` listens to
the first four; `uploadQueueStore` listens to the upload queue.

| Channel                           | Payload               | Notes                                                                                                                                                                                                                          |
| --------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `xfalcon://chat-run-event`        | `RunEvent`            | One type, `state_changed` (`run_id`, `state`).                                                                                                                                                                                 |
| `xfalcon://chat-inference-event`  | `InferenceEvent`      | Types: `started`, `text_delta`, `reasoning_summary`, `tool_call_delta`, `usage`, `context_compaction`, `completed`, `failed`. Deltas are coalesced in Rust before emission (`src-tauri/src/agent/stream.rs`).                  |
| `xfalcon://chat-projection-event` | `ChatProjectionEvent` | Types: `conversation_removed`, `snapshot_replaced`, `run_state_changed`. The conversation-scoped `run_state_changed` is the adoption seam for `chatStore`: it tells the store which run belongs to the conversation on screen. |
| `xfalcon://tool-invocation-event` | `ToolInvocationEvent` | Types: `requested`, `approval_required`, `approved`, `denied`, `started`, `progress`, `completed`, `failed`, `cancelled`. Emitted only after the journal accepted the transition.                                              |
| `xfalcon://upload-queue`          | `UploadQueueV1`       | Composer attachment queue snapshots. Emitted after every queue mutation. `revision` is monotonic for the process, so a consumer ignores an older snapshot.                                                                     |

Events are admitted only for the active conversation's run, via `adoptActiveRun`
plus an admitted-invocation set.

### Skill drop

Rust handles the window's drag and drop for skills in
`src-tauri/src/skills/drop.rs`. The renderer never receives a path.

| Channel                           | Payload                                                | When                                                                                                |
| --------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `xfalcon://skill-drag`            | `"over"` or `"leave"`                                  | While a drag moves over the window or leaves it. Rust sends it.                                     |

## Run and invocation state machines

`RunState` — `crates/contracts/src/lib.rs` (wire values are snake_case). Edges
are the `allowed_transition` function in `src-tauri/src/agent/run.rs`:

```
Draft → Queued → Running ─┬→ Completed
                          ├→ Failed
                          ├→ Cancelled
                          ├→ AwaitingApproval ─┬→ Running
                          │                    ├→ Cancelled
                          │                    └→ Failed
                          └→ Interrupted → Recovering ─┬→ Running
                             (crash; see              ├→ Failed
                             runtime-flows § 5)       └→ Cancelled
```

`ToolInvocationStatus` — `crates/contracts/src/tools.rs`. Edges are the
`allowed_transition` function in `src-tauri/src/tools/invocation.rs`:

```
Requested ─┬→ AwaitingApproval ─┬→ Approved → Running ─┬→ Completed
           │                    ├→ Denied              ├→ Failed
           │                    └→ Cancelled           └→ Cancelled
           ├→ Approved   (standing consent skips the pause)
           └→ Denied
```

There is deliberately **no `Requested → Failed` edge**. Arguments failing a
tool's own JSON Schema are rejected _before_ the invocation is opened, so schema
failures never fabricate invocation history or consume budget.

## The custom URI scheme

`xf-preview` — registered in `lib.rs`, handled by `preview/protocol.rs`.

| Platform        | URL form                           |
| --------------- | ---------------------------------- |
| Windows         | `http://xf-preview.localhost/<id>` |
| Everything else | `xf-preview://localhost/<id>`      |

Use `previewDocumentSrc(id)` (which wraps `convertFileSrc`) rather than building
the URL. Routes: `/<doc-id>` serves a registered document under its kind's CSP;
`/fonts/<file>` serves the bundled product faces so the injected base stylesheet
can reach them under the document's `font-src` rule. Responses are
content-addressed, so caching is `immutable`; an evicted id 404s on the next cold
load. The store holds at most 256 MiB (`PREVIEW_STORE_MAX_BYTES`) and evicts the
least recently served document first.

The scheme is listed in the app CSP as `frame-src xf-preview: http://xf-preview.localhost`
and nothing else. Per-document policies are in
[runtime-flows.md](runtime-flows.md) § 8.

## Plugin permissions granted

Four in `capabilities/default.json`, each the narrowest variant that works. The two
window permissions are in `capabilities/macos-window.json` and apply on macOS only.
The dialog permission (`dialog:allow-open`) was removed. The renderer no longer opens
dialogs. Rust opens them.

| Permission                  | Why this one                       |
| --------------------------- | ---------------------------------- |
| `opener:allow-open-url`     | Open an external link in the system browser or mail app: the `target="_blank"` anchors from `src/ui/Link.tsx`. |
| `opener:allow-default-urls` | The URL scope `open_url` checks: `http:`, `https:`, `mailto:` and `tel:` only. Without it every link is refused. |
| `core:event:allow-listen`   | Receive backend events.            |
| `core:event:allow-unlisten` | Stop receiving them.               |
| `core:window:allow-start-dragging` | macOS only. Drag the window from the app's header (`data-tauri-drag-region`). |
| `core:window:allow-internal-toggle-maximize` | macOS only. Zoom the window on a double-click of the same header. |

The Rust side still uses the dialog plugin for the folder and skill pickers and
the save dialogs. Desktop updates use the typed `update_check`,
`update_install`, and `update_restart` application commands. The renderer has
no direct updater or process plugin permission.

The plan providers add no plugin or core permission. The two macOS window permissions in the list above come from the window header, not from the plan providers. The ChatGPT sign-in page opens from Rust, not from the webview.
