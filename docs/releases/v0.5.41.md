# xFalcon Desktop v0.5.41

Changes since v0.5.40:

This release is about speed: a faster start, faster screens, faster answers and a faster send. Nothing was toned down. Animations, the typewriter reveal and every feature work as before.

- **Faster start and a smaller app.** The first screen appears 17% sooner (352 ms to 292 ms) and the workspace is ready 8% sooner (594 ms to 546 ms). The app ships 76% less CSS (588 KB to 139 KB) and 23% less main JavaScript (1,267 KB to 973 KB). Settings, Projects, Datasets, Reports, chat export and the side panel load the first time you open them, and the app fetches them in the background shortly after it starts, so opening one does not wait. While a screen loads, the previous one stays on screen.
- **Datasets and Reports reopen faster.** Going back to Datasets or Reports shows the last list at once and refreshes it in the background, instead of starting from a blank screen. If the refresh fails, the screen shows the error as before. With a slow connection to the workspace (120 ms per call), Datasets reopens in 295 ms instead of 642 ms and Reports in 325 ms instead of 564 ms.
- **Large folders are quicker.** Reopening Projects takes 138 ms instead of 229 ms with 4,000 files in the folder. Typing in the file filter of a 20,000-file folder takes 32 ms per keystroke instead of 979 ms, and filtering inside an open CSV takes 28 ms instead of 130 ms.
- **HTML answers stream without freezing.** A long HTML document in an answer is drawn as a preview card, and its source was being syntax-highlighted on every update for nothing. That work is skipped. Streaming a 60 KB HTML answer takes 2.4 s instead of 12.9 s, with no UI freezes (82 before).
- **The composer and message rows stay still while an answer streams.** The composer no longer redraws for every streamed token (80 redraws for 80 tokens before, none now). Typing in a message you are editing no longer redraws every other message (780 redraws for 20 keystrokes before, none now).
- **Sending starts sooner.** The message request leaves 35% sooner (380 ms to 247 ms with a slow connection to the workspace), because the sidebar refresh now runs after the send, not before it. A failed refresh behind a send never hides the send's own error.
- **Fewer round trips behind a send.** Connections to the workspace service and to the model providers are reused instead of opening a new secure connection for every call. The check that you may open the conversation and the read of its model now run together, which saves one round trip, and tool-server discovery runs while the conversation context loads. Sign-in and workspace reads run in parallel and report errors in the same order as before. Tool approvals and a few other local commands no longer hold up the app while they read the local database. The conversation title is still written with the same key the answer used.
- **Benchmarks for developers.** `npm run perf` runs browser benchmarks for startup, screen opens, scrolling and streaming against a mocked backend, and `npm run perf:compare` prints a before and after table for two runs. New tests cover lazy view loading, connection reuse, the send path and the HTML answer highlighting.

### What changed for chat answers

Already optimised in earlier releases: the streaming hot path (fence-card renders per answer went from 500 to 60, and transcript cost from about 910 ms to 34-120 ms), the virtualised 10,000-message transcript and the typewriter reveal.

Optimised in this release: HTML answers, the composer and message rows while streaming, the moment a send leaves the app, and the backend round trips behind a send, as listed above.

Not changed: the time to the first word of an answer, which depends mostly on the model provider.

### How to read these numbers

- The figures are medians from headless Chromium at 4x CPU slowdown against a mocked backend. They show relative change, not real-app timings.
- Scrolling a 10,000-message chat, scrolling a 1,500-conversation sidebar, opening a 200 or 10,000-message chat, the command palette, and the first open of Datasets, Reports, Settings and Chats were already smooth and are unchanged within about 3%.
- Without backend delay, Datasets and Reports reopen only 6-8% faster. The large gains show up when the backend is slow.
- The backend gains (shared connections, overlapped reads) were checked with tests that simulate network delay and were not measured against the live service. Expect tens to low hundreds of milliseconds per send, not a multiple.
