# SOC 2 control mapping for the desktop application

Version 0.5.50 · reviewed 2026-10-28 · **Reference** · audience: external auditors, compliance owner, desktop engineering

This document maps the AICPA Trust Services Criteria to the xFalcon Desktop application. For each criterion it says what the desktop app does, what another system owns, and what the organisation must still provide. It names the code and tests that support each claim. The control matrix for the same product is in [compliance.md](compliance.md). The threats are in [threat-model.md](threat-model.md). The external proof that is still to come is in [assurance-plan.md](assurance-plan.md).

> **This is a traceability and plan baseline, not a certification, attestation, or audit opinion.** It does not claim that any control operates effectively. It makes no estimate of any audit outcome. Evidence cells name repository paths and historical test names checked on 2026-10-13. Current-source test and static evidence is listed in [assurance-plan.md](assurance-plan.md#staging-validation-evidence-2026-10-15). Items marked **UNVERIFIED** were not confirmed on a real system.

## a. Purpose and scope

**In scope:** the xFalcon Desktop application (this repository, `src-tauri/` and `src/`, plus the shared `crates/contracts`). This covers the Rust core, the React interface, the release and update chain for the desktop app, and the data the app stores on the device.

**Out of scope:** the MCP server, the DA (data and agent) service, Casdoor (identity), xfalcon-web, and every other system. Each is audited separately. Where a criterion depends on one of them, this document marks it **Inherited** and names the owner. It is never recorded as a desktop gap.

**Assumptions:** one user per device. The desktop app is the only component that runs on the user's device. The user's device, its disk encryption, and its operating system are the organisation's responsibility.

## b. How to read it

### Status vocabulary

The first four statuses come from [compliance.md](compliance.md). The last two are added for this document.

| Status           | Meaning                                                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Evidenced**    | An observed command or a named test shows the desktop side of the requirement in this repository.                            |
| **Partial**      | Some evidence exists. A specific named piece is missing.                                                                     |
| **Planned**      | The requirement and owner are defined. Implementation or test evidence is not yet sufficient.                                |
| **Gap**          | The observed repository state conflicts with the requirement. Release-blocking.                                              |
| **Inherited**    | Another system or team owns the control. The owner is named in the row. The desktop side is only its integration obligation. |
| **Organisation** | A company-level policy or process, not software. The desktop app contributes the artefacts named in the row.                 |

**IT-owned** and **planned** are used in the owner column. IT-owned means the GitHub organisation settings are run by the IT team. Planned means the item is defined and scheduled but not yet in place.

### Alignment with compliance.md

[compliance.md](compliance.md) was updated on 2026-10-13 to match the code. This document agrees with it on these points:

- **Erasure (CM-005, CM-029).** The account clear (the first step of Reset xFalcon) handles the account's `chat-model.json`, `custom-model-settings.json`, `skills/` and `.skills-staging/`. Its device sweep also removes `standing-tool-approvals.json` and the legacy root `skills/` folder (`src-tauri/src/security/account_cleanup.rs`). The account clear keeps `audit/`, `logs/`, `EBWebView/` and `migrations/`; the full purge removes them. Reset xFalcon (CM-033) is the only in-app erase. It runs the account clear, then the full purge in a helper after the app exits, then relaunches the app.
- **Audit trail (CM-009, CM-027).** The audit hub opens at start-up, and its publisher is passed to projects, approvals and chat (`src-tauri/src/lib.rs`). Events stay on the device. No central store or alerting exists.
- **Sign-in, redirects and DNS (CM-006, CM-008, CM-019).** The OAuth nonce is compared on the signed access token at sign-in; a wrong or empty claim fails closed and an absent claim is accepted (`src-tauri/src/auth/service.rs`, `nonce_matches`). Workspace discovery uses `build_discovery_client()`. While `ENFORCE_PUBLIC_MCP_HOSTS` is `true`, registered MCP DNS names are resolved through `PublicOnlyResolver` (`src-tauri/src/mcp/dns.rs`), and behind a system or environment proxy the resolver does not run (ADR-054). The switch is `false` today, so the resolver is not installed (ADR-057).
- **Session, inactivity and reporting (CM-006, CM-034, CM-035).** A session that gets no input for 12 hours is signed out (`src/app/useIdleSignOut.ts`). The session store refuses stale writes (`src-tauri/src/auth/session.rs`). The Application section of Settings has a "Report a security issue" link that opens an e-mail to the support mailbox. Real-machine behaviour of all three is **UNVERIFIED**.
- **Settings entry (CM-005, CM-029, CM-033).** Reset xFalcon is the only erase action in Settings > Data & reset. The Clear local data row, its dialog and `local_data_clear` were removed (ADR-056). The Account menu holds Sign out only, and the old visibility flag is removed (`src/features/settings/DataResetSection.tsx`).

The fact that a rule is now implemented does not make it verified on a real device. Items that need a real device are marked **UNVERIFIED** in the table rows.

## d. Accepted by design

The three items below are product decisions. They are not gaps. Each has compensating controls. The first two were made by the product owner. The third is open for confirmation by the customer success and on-prem owners. All three are recorded in [decisions.md](decisions.md).

### Tool-call auto-approval (ADR-008, TM-006)

Tool calls run without a prompt by default. This is intentional. An operator can restore a prompt for every call with `XFALCON_REQUIRE_TOOL_APPROVALS=1` (`src-tauri/src/tools/standing.rs`).

Compensating controls:

- The policy engine checks every call against an allowlist and a risk class (`src-tauri/src/tools/policy.rs`; `src-tauri/src/approvals/policy.rs`). Denials are tested (`tools::tests::policy::denies_when_tool_not_in_allowlist`).
- Tool ids that the app creates for itself use a reserved `__internal__` prefix (`src-tauri/src/tools/registry.rs`). This is not a general namespace for every MCP tool id.
- Each chat run has its own run-scoped state (`src-tauri/src/agent/run.rs`).
- Tool results are data and cannot change a later policy decision (`agent::tests::tool_loop::prompt_injected_tool_result_cannot_alter_a_later_policy_decision`).
- Inputs are validated against schemas before a call (`crates/contracts`; `src-tauri/src/mcp/catalog.rs`).
- Sensitive files are denied to tools (`src-tauri/src/projects/sensitive.rs`; `projects::tests::sensitive`).
- Budgets bound the number of calls per run (`src-tauri/src/tools/budget.rs`; `src-tauri/src/agent/tool_loop.rs`).
- In the chat loop, every decision and execution is recorded in the local audit log as `tool.approve`, `tool.deny` and `tool.execute`, with the tool id as detail. Plans applied through the approvals service carry the plan id and no tool id (`src-tauri/src/audit/event.rs`).

Known limit: the audit log is local and has no alerting. A mutating MCP tool runs without a human prompt by default.

### Agent edits to project files without review (ADR-043, TM-020)

When an agent changes a file in a trusted project, the change applies without a review step. This is intentional.

Compensating controls:

- Only files inside a trusted project can be changed (`src-tauri/src/projects/trust.rs`; `src-tauri/src/projects/path_policy.rs`).
- Paths are confined to the project root with `cap-std`. Symlinks and reparse points are refused. Writes are atomic and race-checked (`src-tauri/src/projects/writer.rs`; `projects::tests::path_policy`; `projects::tests::writer`).
- Sensitive files are denied (`src-tauri/src/projects/sensitive.rs`).
- Every file keeps up to 50 revisions, and the account has a 512 MiB cap. A revision can be restored (`src-tauri/src/projects/backup.rs`; `docs/operations.md`, restore a file the agent changed).
- Base hashes stop an edit that was made on an old version of the file (`src-tauri/src/projects/patch.rs`).

Known limit: project writes appear in the audit log as `tool.execute`. Plans applied through the approvals service carry the plan id and no tool id. There is no separate `project.write` event. No setting restores review of project writes.

### Private-host switches for on-prem and private deployments (ADR-057, TM-005)

Two constants switch off the public-host rules for registered MCP servers, and the https-only rule for presigned URLs. Both are `false` in the current code. A registered MCP server may be on a private address or on a name that resolves to one, and a presigned URL may use plain http to any host. On-prem and private deployments cannot meet the public-host rules, so this is accepted for them and is open for confirmation.

Compensating controls:

- Redirects are not followed on the MCP and presigned-URL clients. A registered server receives only its own credential.
- OAuth servers still need sign-in. The bundled tenant server is unaffected.
- Setting either constant to `true` restores the earlier rule in one edit, and the enforcement code is tested in both positions (`mcp::tests::registry`, `uploads::tests::da_repository`).
- Custom model endpoints accept any `http` or `https` host by design (ADR-061); the device does not restrict where a private model URL points.

Known limit: a presigned URL sent over plain http can be read on the network path until it expires, because the URL is the credential.

## h. Notes on the judgements in this mapping

- **CC6.8 is Partial, not Gap.** The release workflow is set up to ship an unsigned Windows build when no certificate is configured. The current macOS release process requires signing; verify later packaged candidates in [Packaged-binary verification](assurance-plan.md#packaged-binary-verification). The remaining gap is Windows Authenticode signing; it is recorded in [compliance.md](compliance.md) as CM-026 and in its ranked list.
- **Reset xFalcon and the NSIS uninstall rules (`/UPDATE` and `$EXEDIR`) are UNVERIFIED on real machines.** They are recorded as CM-033 and CM-029. C1.2 and CC6.5 stay Partial until a real-device run exists.
- **C1.2 is Partial, not Evidenced.** The guidance rated disposal as Evidenced. Real-device disposal is **UNVERIFIED**, so Partial is the honest rating.
- **CC7.1 and CC8.1 name IT-owned items.** Those items are not counted against the desktop app. They are listed so that auditors can see them.
- **Current source limits (v0.5.42).** These are recorded as limits, not as gaps closed. The session races listed in [security.md](security.md#identity-and-secrets) (CC6.2, CC6.3). The log redaction gaps listed in [security.md](security.md#log-content-and-redaction) (CC7.2, C1.1). Unresolved required roots make a purge incomplete. The legacy shared-temp snapshot path is intentionally left untouched because ownership cannot be proved; verify ownership before any manual cleanup (CC6.5, C1.2). A skill selection over 4,096 paths is refused, but skills are still not signed (CC6.8). Whole oldest audit segments can be removed as pruning (CC7.2).
- **Verification depth.** Historical rows retain their 2026-10-13 observation dates. The changed staging surfaces were covered by final Windows and Linux test runs; exact counts are in [assurance-plan.md](assurance-plan.md#staging-validation-evidence-2026-10-15). Passing tests do not verify real packaged binaries, OS credential stores, or live services.
