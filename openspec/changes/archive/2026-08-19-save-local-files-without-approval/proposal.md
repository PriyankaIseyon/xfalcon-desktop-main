# Save local files without an approval step

## Why

Editing a file in the project viewer ended in **Send for approval**, followed by
a banner reading "Nothing has been written yet. Review the change and approve
it to save it to disk." Then a sheet showed a unified diff of the change, and a
second click applied it.

Nobody is on the other side of that review. These are local files in a folder
the operator picked and trusted, and the person clicking approve is the person
who just typed the change — they are being asked to review their own
keystrokes, one screen after typing them. The step adds two clicks and a modal
and decides nothing.

It was also already asymmetric. An agent's `project.propose_patch` never waited
for anyone: `ApprovalsService::apply` applies its own plan inside the same tool
call, on the stated grounds that trusting a project _is_ the consent to write in
it. Only the human path was made to ask, and only the human path had the least
to gain from asking.

## What Changes

- **Save writes.** The viewer's primary action becomes **Save**, next to
  **Discard changes**. It writes and reports what happened: a success names the
  file, a failure names the reason and keeps the draft, because those bytes are
  the only copy.
- **The review surface goes.** `ApprovalSheet`, `useApprovals`,
  `ApprovalErrorBoundary`, `FileDiff`, `diffParser` and the hand-written
  `approvals-types` are removed, along with the `approval_propose_patch` and
  `approval_resolve` commands, their generated permissions and their capability
  entries. `ToolApprovalPrompt` is untouched — approving one _tool call_ mid-run
  is a different question with a real second party.
- **One command replaces two.** `project_save_file(project_id, path,
content_base64)` proposes and applies a single-file plan in one call, through
  a new `ApprovalsService::save` built on the same `apply` the agent path uses.
- **Nothing else about the write changes.** The plan is still proposed against
  the current trusted root, persisted, journaled and audited, and
  `projects::execute` still re-validates containment, writes atomically and
  preserves permissions. What is removed is a question, not a control.
- **No re-read after save.** Editing is only offered once the whole file is on
  screen, so the bytes just written are the file; the viewer shows them
  directly rather than paging a long file again to arrive at the same content.

## Capabilities

### Added Capabilities

- `project-file-editing`: how a person's own edit in the file viewer reaches
  disk.

## Impact

- `src-tauri/src/approvals/{commands,service,policy}.rs`: one save command, one
  service method; `ApprovalDecision::deny` becomes test-only, since no caller
  denies any more but `resolve`'s refusal to write on a denial is still an
  invariant worth holding.
- `src-tauri/src/lib.rs`, `build.rs`, `capabilities/default.json`,
  `permissions/autogenerated/`: two commands out, one in.
- `src/features/projects/ProjectFileViewer.tsx`: Save and Discard.
- `src/features/approvals/`: only `ToolApprovalPrompt` remains.
- `src/app/AppShell.tsx`, `src/features/projects/ProjectExplorerView.tsx`: the
  operations no longer route through the shell at all.
